# IMP-COMMIT001 Crash-Safe Commit Consistency Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a ProjectGuard transaction recoverably committed through one immutable canonical Dropbox record before derived materializations or local SQLite are advanced.

**Architecture:** Add a revision-addressed canonical commit record containing the transaction, resulting state, event, and receipt. ProjectGuard reconciles contiguous records before applying new work, repairs interrupted materialization idempotently from the record, and persists local SQLite only after derived state succeeds. Existing V2 snapshots remain the backward-compatible baseline for revisions that predate commit records.

**Tech Stack:** TypeScript, Cloudflare Workers Durable Objects/SQLite, Dropbox API transport, Vitest + `@cloudflare/vitest-pool-workers`.

**Spec:** `docs/commit-consistency.md`

## Global Constraints

- Production continuity mode remains `stable` throughout this package.
- No user recovery command, migration command, version selection, or chat-specific instruction is introduced.
- Existing pre-upgrade V2 projects with no historical commit records remain valid baselines.
- A canonical commit record is immutable and revision-addressed; no mutable commit-head pointer is introduced.
- The deterministic fault-injection harness must reproduce the post-record/pre-local failure window.
- ProjectGuard never skips a malformed, non-contiguous, or project-mismatched commit record.

- [ ] **Step 4: Implement reconciliation and new commit sequence**

Before transaction receipt lookup/application, start from local state or V2 snapshot, absorb the record for the baseline revision when local is absent, then probe contiguous `revision + 1` records. For each recovered record, materialize idempotently and persist state+receipt. For a new V2 commit: publish record, materialize it, then persist local state/receipt. On any failure after record publication, leave local persistence unadvanced so the next request is forced through reconciliation.
